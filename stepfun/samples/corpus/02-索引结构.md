# 索引结构：B+ 树为什么是默认选择

## 为什么 B+ 树比哈希索引更适合范围查询

- **有序**：B+ 树的所有键在叶子层按顺序排列，叶子节点还用双向链表串起来。范围查询 `WHERE id BETWEEN 100 AND 200` 只要定位起点再顺序扫链表。
- **哈希索引只有等值**：哈希把键映射到桶，天然无序，`> < BETWEEN ORDER BY` 全部用不上，只能全表扫。
- **前缀匹配**：`LIKE 'abc%'` 在 B+ 树上可以走范围扫描，哈希索引完全无能为力。

## 为什么不用 B 树

B 树每个节点都存数据，扇出小、树更高，一次磁盘 I/O 读到的键更少。B+ 树非叶子节点只存键和指针，扇出更大，三层就能存两千万行左右（InnoDB 一页 16 KB）。

## 聚簇索引与二级索引

- **聚簇索引**：主键索引的叶子节点直接存整行数据，一张表只有一个。
- **二级索引**：叶子节点存主键值。查非索引列要回聚簇索引再查一次，叫**回表**。
- **覆盖索引**：查询需要的列都在二级索引里，就不用回表，`EXPLAIN` 的 Extra 显示 `Using index`。所以把常用查询列一起放进联合索引，可以显著减少回表。

## 最左前缀原则

联合索引 `(a, b, c)` 支持 `a`、`a+b`、`a+b+c`；跳过 `a` 直接用 `b` 用不上索引。范围条件会截断后面的列：`a=1 AND b>2 AND c=3` 里 `c` 用不上索引的有序性。

## 索引失效的常见场景

- 索引列上做函数或运算（`DATE(created_at)=...`）
- 隐式类型转换（字符串列和数字比较）
- 前导模糊 `LIKE '%x'`
- `OR` 两侧列不同索引
- 选择性太差的列单独建索引

## EXPLAIN 要看的字段

`type`（const > eq_ref > ref > range > index > ALL）、`key`、`rows`、`filtered`、`Extra`（`Using index` / `Using filesort` / `Using temporary`）。
