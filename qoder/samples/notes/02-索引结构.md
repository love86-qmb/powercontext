# 索引结构笔记

## 为什么是 B+ 树

B+ 树把所有数据都放在叶子层，非叶子节点只存键，所以同样大小的页能装下更多键，树的高度被压得很低，几千万行的表通常三层就够了，一次查询的磁盘往返次数也就固定在三四次以内。叶子节点之间用双向链表串起来，范围扫描顺着链表走，不需要回到上层反复找路径。

对比二叉搜索树，它的高度失控，最坏退化成链表；对比 B 树，B 树每个节点都带数据，页里能存的键更少，树更高，而且没有叶子链表，范围查询要中序回溯。

## 为什么不用哈希索引

哈希索引等值查询是 O(1)，看着更快，但它只支持等于，不支持范围、不支持排序、不支持最左前缀匹配，因为哈希打散了顺序。一旦遇到 between、order by、like 前缀匹配，哈希索引整个用不上。而且哈希冲突严重时性能会退化，不同键撞进同一个桶就要在桶内再遍历。

真正的原因还是存储引擎要同时服务等值和范围两类查询，B+ 树是唯一能两头都顾上的结构。哈希的强项被 InnoDB 用另一种方式吸收了：自适应哈希索引由引擎自己按热点页动态建，不需要人工干预。

## 回表是什么

二级索引的叶子节点存的是索引列加主键值，不含其他列。用非覆盖的二级索引查不需要的列时，引擎拿到主键还得再回到主键树查一遍整行，这第二次查找就是回表。回表的代价是随机 IO，命中一千行就是最多一千次回表，所以慢查询里回表行数往往比扫描行数更能说明问题。

## 覆盖索引

如果查询要的列全部包含在二级索引里，就不用回表，这种索引叫覆盖索引。判断方法是看执行计划的 Extra 是否出现 Using index。实践上常见做法是把高频查询的过滤列和返回列一起放进联合索引，用空间换掉回表；反过来 select 星号 会让覆盖索引失效，因为总得回表取其余列。
